# 从使用者决策定义 EvalAnchor 0.2

## 服务谁，解决什么决策

假设一支团队维护客服订单 Agent，正在更换模型、调整提示词，或降低调用成本。团队需要回答：候选配置是否能完成查证、取消、退款和地址修改任务；是否会请求未经授权或未经确认的写操作；发生超时后是否产生重复副作用；改善是否值得额外费用。

这是一项工程作品集中的明确使用场景，不是已经验证的客户需求或商用部署。项目目标是交付可运行、可检查、可复现的决策流程，而非用功能数量或模型榜单数字替代价值。

## 一次完整工作流

1. 维护者冻结世界、任务组、开发/测试划分、目标配置、接受规则和预算。
2. 开发者先在开发集检查工具接口和提示策略；所有失败保留，不将开发成绩当确认结果。
3. 执行器调用真实模型，实际运行本地模拟工具，逐请求记账，逐任务持久化证据。
4. 复核器从初始世界重新执行每一步工具请求，核对原生响应、参数、结果、最终状态和评分。
5. 工作台展示四配置矩阵、任务族差异、失败轨迹、费用和审核意见；按冻结规则给有限套件决策。
6. 发布者提供源码、许可证、数据卡、原始轨迹、预算流水和可重算的验证入口。

## 目标与验收的对应关系

| 决策问题 | 工程机制 | 可验证结果 |
|---|---|---|
| 回答正确但操作错误怎么办 | 最终状态与事务账本 oracle | 仅口头声称已退款、修改金额或重复写入均不通过 |
| 防护拦住错误是否代表模型安全 | 违规尝试、已执行错误分别计数 | 被拒绝的危险 commit 仍进入模型的违规尝试指标 |
| 超时之后能否恢复 | 幂等操作键、操作查询、模型请求缓存与持久预算 | 不重复支付已保存请求；不重发计费结果不明的请求 |
| 多运行几次是否把证据夸大 | case/repeat完整网格、相关变体共享group | 重复和改写不增加独立情境组数 |
| 低成本配置是否值得采用 | 同模型提示对照、跨模型次要对照、费用覆盖与Pareto | 成本未知不当零；开发集和删题子集不能获得发布通过 |
| 失败在哪里，谁复核过 | 原始调用回放、证据指纹绑定审核历史 | 修改证据后旧审核失效；伪造评分/状态在加载时被拒绝 |

## 本轮完成边界

本地模拟业务环境使用自建合成实体，不连接真实支付或订单系统。可信用户回复由确定性事件脚本提供，避免用户模拟器引入额外费用和随机评分；因此不声称覆盖自然对话的所有变化。参考脚本只验环境可达性。真实模型成绩来自原生 Responses 工具调用。

完整测试集是48条、24个相关情境组。两模型、两提示策略、每条两次重复产生384条确认轨迹；统计区间仅描述这批组的变动，不宣称随机生产流量上的置信保证。测试后不得调整提示再把同一测试集称为未见确认集。

任务成功、尝试违规、实际错误状态、证据有效性与成本是独立维度。最终失败或不确定结论也是项目有效产出，不通过删题、补写模型输出或事后调整门槛获得漂亮结果。

保留v0.1的Inspect/Promptfoo实际日志往返与严格合同审计。v0.2新增可执行订单世界、原生多步Agent循环、持久预算、轨迹重放和工作台。多步工具任务、最终状态评分、bootstrap和发布门禁都有成熟先例；差异与取舍见[目标审查](../research/v2-goal-review.md)。本项目的价值在于把这些环节实现成可复核的完整工程，不宣称新算法或官方τ-bench成绩。
