# v0.3 审查与改进决定

审查日期：2026-11-06。基线为 v0.2.0（`046b0ee7c78c7057959f5bd9fcbb884497fe94cc`）。本轮先由三个独立 agent 分别审查评价方法、产品流程与发布工程，再分工实现；最终仍需整体验证，分工不代替验证。

## 本轮要解决的问题

一个维护订单客服 Agent 的开发者已经有当前方案和候选方案。他需要知道：候选是否完成更多任务，是否在关键任务上退化，多花的钱是否在可接受范围内；如果不能升级，应该具体检查哪些轨迹。

v0.2 提供原始证据与总体接受合同，但使用者仍要自行拼接多张结果表。当前项目的首要缺口是从可审计证据得到明确、可解释、可自动执行的升级判断。

## 审查发现及处理

| 审查发现 | 影响 | v0.3 处理 |
|---|---|---|
| 总体门槛为 80%，没有任务族门槛 | Terra checklist 主测试 77/96 通过总体合同，但 injection 0/12 | 新建独立升级政策，按总体、任务族、相对退化和成本分别检查 |
| 原有分析未强制检查执行器/评分器身份 | 在内存副本中删掉 engine_hash 或改 scoring_version，旧分析仍能返回通过 | 新升级入口核对已注册执行器与评分器身份；身份不明不能通过 |
| 首次页面嵌入全部实验 | 紧凑 JSON 约 72.5 MiB，查看一个失败也要先加载所有轨迹 | 在线模式按需读取摘要与单条轨迹，离线导出仍完整 |
| run/budget 写死历史活动编号和 4.75 美元 | 新活动不能独立配置；非默认账本无法查询 | 显式活动 ID 和预算，账本查询用只读连接，拒绝重置历史上限 |
| analyze 写回 experiment.json | 文件指纹及已有审核绑定会变化 | 只写独立分析文件，拒绝输出覆盖输入及硬链接别名 |
| 恢复完成实验时可指定新账本 | 无需再发请求也可能把旧轨迹配上零费用回执 | 恢复前绑定活动、上限、原账本和逐请求回执，拒绝费用重置 |
| 失败执行仍可能写回旧预算回执 | 拒绝运行却修改了原始材料 | 凭据访问前检查输出与 journal，失败不覆盖旧回执 |
| 源码包与 ZIP 的文件排除规则不同 | 本地私有配置可能进入常规构建产物 | 统一发布文件策略，并用虚构敏感文件验证构建边界 |

审查只在内存副本或临时目录中构造反例。历史原始轨迹、冻结评分器、业务环境和已经报告的成绩不改写。

## 为什么选择这条路线

比较了三类方案：扩大模型/任务数量、增加主观 LLM 评分、完善从证据到升级决定的闭环。前两类可以拓展覆盖，但都不能解决已经出现的“总体通过却整族失败”。本轮优先完成决策闭环与实际可用性。

Inspect 已经提供日志 API、轨迹查看和分析工具；Promptfoo 已有条件断言、阈值和成本检查。v0.3 不把这些成熟能力包装成新算法，而把它们的设计原则落实到本项目的订单状态重放、明确升级目标和可定位退化案例中。

来源：

- [Inspect 官方日志文档](https://inspect.aisi.org.uk/eval-logs.html)，2026-11-06 核对：日志状态与原始样本是分析前提。
- [Promptfoo 官方断言与指标文档](https://www.promptfoo.dev/docs/configuration/expected-outputs/)，2026-11-06 核对：用明确条件检查输出，阈值不是普适结论。

## 证据范围

新政策在已经看过的历史数据上演示，因此标记为事后复核。它不追溯修改 v0.2 的预设合同，也不把新阈值称为预注册。通过仅表示满足给定政策下的有限套件条件。政策应根据业务容忍度设置；同一数据上反复调阈值不能形成独立确认结果。

本轮改进不依赖新模型生成：历史数据已包含能够区分政策效果的失败和成本反例，软件边界可由离线回放与故障测试验证。未来若更改 Agent 提示或业务环境，应建立新的实验身份和留出任务，再运行真实模型。
