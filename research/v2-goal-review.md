# EvalAnchor v2：从输出验收到 Agent 升级决策

核验日期：2026-10-29。本文是独立设计审查与实施建议，不是功能完成记录，也不是实验结果。用户确认的目标是完整、高质量的求职作品集，允许本轮 API 总预算不超过 5 美元，并最终发布到本人 GitHub。本次审查只读现有实现、检索官方源码及论文；没有读取密钥、没有调用模型 API。

方法采用本地 `brainstorming-research-ideas` 技能的机制族比较、最近邻反证和最小判别验证。以下路线选择、数值门槛和样本规模均为 AI 的实施建议；项目最终实现或预注册文件若另有明确约定，应按实际协议说明，不应把本建议写成用户已确认的业务 SLA。

## 1. 先确定用户和决策

**目标用户：负责订单售后 Agent 的应用工程师。目标决策：是否用候选模型、提示词或执行预算替换现有版本，以及成本增加是否买到了可观察的任务完成能力。**

具体情境：一个客服 Agent 可以查询订单、检查取消/退款政策、生成变更预览并在确认后提交。升级后，回复更自然、平均字段正确率更高，但它可能给错订单退款、重复提交、在超时后误称成功，或为了低成本过早结束。工程师需要看见业务是否完成、有哪些不允许的副作用，以及支持这个判断的原始证据。

建议两句话定位：

> EvalAnchor 在可重放的订单沙盒中运行客服 Agent，用最终业务状态和完整工具事件检查任务完成及关键回归。它将冻结测试、原始模型请求、工具副作用、成本和版本决策放在同一条证据链中，帮助开发者判断一次 Agent 升级是否值得继续推进。

这个用户需求是合理的工程假设，尚无真实公司访谈或线上工单数据支持；不能宣传为已验证的市场需求。作品集的证据应是可运行产品、真实实验、失败归因和改进闭环，而非只有项目规模、框架名称或测试数量。

## 2. 现有 v1 做到了什么，还缺什么

本次查看了 README、`runner.py`、`metrics.py`、`openai_provider.py`、架构/数据卡和已有研究文件。

| 已有证据 | 能支持的结论 | 仍缺的闭环 |
|---|---|---|
| suite/run 合同、原始输出重评分、严格可比性、SQLite 恢复 | 固定输入和评分协议下的记录可审计 | 缺少执行中的工具状态、逐步观察、终止与恢复语义 |
| `tool_call` 精确检查 name/arguments，明确 `executed=False` | 模型输出了某个期望结构 | 不能证明工具被执行、业务完成、未产生额外副作用 |
| 64 条手写合同、同组语言/措辞变体 | 有限样例上的合同回归 | 缺少开发与最终测试隔离、变体有效性检查、测试后修订记录 |
| Inspect / Promptfoo 真实 fixture 往返 | 已验证该导出协议的互操作 | 不是多轮 Agent 的状态证据互操作，不能沿用声明自动扩大范围 |
| Qwen 2/16、Luna 15/16 的真实单轮记录 | 有限静态合同上的推理结果 | 不是 Agent 成功率，不能作为 v2 闭环有效性的实验 |
| 三态统计门禁、离线报告 | 保守区分有限证据和总体推断 | 缺少业务验收结果、候选选择理由、成本约束与下一步动作 |

另一个实施约束：当前 OpenAI adapter 有意拒绝工具输出、限制最多 32 次请求和 0.05 美元额度；这是 v1 smoke 的安全边界。v2 需要单独的 Agent 请求协议、全实验账本和预算实现，不能只是放大常量后声称支持多轮工具调用。

## 3. 三条机制不同的路线

### A：执行状态驱动的业务验收——建议主线

- **机制**：把模型接入真实执行的本地订单工具；从初始状态、工具事件、最终状态和任务谓词判定完成，独立检查全程不变量。
- **解决的问题**：回答正确或工具参数正确，却没有完成业务，或者产生了错误写入。
- **最近邻**：τ-bench 的 DB/ENV_ASSERTION、Inspect 的工具循环与自定义 scorer、Promptfoo 的 Agent trajectory 与状态任务集成。
- **适用条件**：业务规则能明确写成机器可检验约束；任务状态与用户授权来源可被可靠记录。
- **最强反对意见**：这只是更小、更容易、没有真实用户的 τ-bench；工程师也可以用 Inspect 加 pytest 实现。
- **判别验证**：构造“最终答案正确但状态没变”“最终状态相同但发生过重复扣款再撤销”“不同正确路径达到相同结果”三类反例。分别必须失败、失败、通过。若评分器做不到，不应先花 API 跑大表。
- **资源代价**：开发中等；确定性工具无需模型费用；主要费用是被测 Agent 多轮推理。
- **保留理由**：直接补足现有项目最关键的业务含义，能形成可解释的求职演示。

### B：测量有效性与抗过拟合审计——作为挑战路线

- **机制**：冻结开发/测试划分，对同一潜在情境施加有明确预期的变换，检查评价规则本身是否错把措辞、路径或编号当能力。加入错误 Agent 与错误评分器的 mutation tests。
- **解决的问题**：一个漂亮的分数究竟测到了能力、模板记忆，还是评分漏洞。
- **最近邻**：Unitxt 的模板/示例矩阵和分组评价；τ-bench 的冻结 task pack；已有论文对 benchmark holdout 的分析。
- **适用条件**：能明确说明变换保持什么语义，或应如何改变预期结果。不同语言不是天然等价，更不能仅以自动翻译声称等价。
- **最强反对意见**：少量人工扰动不能代表自然分布，变换本身还可能改变难度或政策含义；只有自测评分器容易循环论证。
- **判别验证**：实体重命名和工具结果字段顺序变化应保留业务 oracle；授权从“同意”改成“不同意”则必须反转允许写入的约束。若某种变换没有可靠 oracle，留作人工诊断，不进入正式成功率。
- **资源代价**：大部分离线，少量真实扰动测试；需要认真审查数据而不是增加依赖。
- **保留方式**：本轮至少实现分组隔离与明确有效的扰动；完整“评测器研究平台”暂不独立扩展。若 A 的任务过于简单、所有配置都满分，此路线优先重新打开。

### C：成本与质量约束下的配置选择——作为决策层

- **机制**：在固定业务协议下比较模型、提示词及推理步数预算；先过滤不满足关键约束的配置，再给出有限样本的成本—成功率 Pareto 前沿与选择理由。
- **解决的问题**：更贵模型是否值得、增加步骤是否有效、哪个版本满足部署预算。
- **最近邻**：Promptfoo 的模型/prompt 矩阵；《AI Agents That Matter》对成本—准确率、holdout 和可复现评测的讨论。
- **适用条件**：保留每次实际请求的用量、缓存、价格日期和失败账目；不同配置面对同一套件/工具/政策，允许改变的目标参数事先声明。
- **最强反对意见**：小样本排序不稳定；用大量变体在同一测试集上挑冠军等同于测试集调参；只有两个模型并不能证明通用最优路由。
- **判别验证**：先在 dev 选择候选并冻结。test 上若便宜方案在关键约束、任务成功和成本均不劣，就必须允许结论是“无须升级”；若候选仍失败，也应交付真实失败和拒绝升级结论。
- **资源代价**：API 最容易扩大的一条路线；本轮不训练路由模型，不在线探索，也不把自适应重跑隐藏为一次评测。
- **保留方式**：作为 A 的最终决策页面；全自动路由与最优策略学习暂缓。

建议组合是 **A 提供业务真值，B 防止自欺，C 产生行动建议**。这不是三个新算法的组合，而是三个问题层次。若用户真正只需要通用模型排行榜，A 应重开而不是强行扩成全领域 benchmark。

## 4. 近邻核验改变了哪些设计

### τ-bench：状态评分和冻结集均已有成熟实现

当前 `sierra-research/tau2-bench` 的 README 已标为 **τ-bench 2.0**，并非只停留在 2025 年 τ² 论文。其 `text-v1` 使用六种语言和三个领域的冻结任务集；README 明确说明 2.0 英文输入与 1.x 不同，不能混比。旧 `tau-bench` 仓库明确任务已过时。因此不能选择旧 retail 任务跑出数字，再和新榜单比较。[当前 README](https://github.com/sierra-research/tau2-bench/blob/main/README.md)，[旧仓库警告](https://github.com/sierra-research/tau-bench/blob/main/README.md)。

官方 [evaluation.md](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md) 区分 DB、ENV_ASSERTION、COMMUNICATE、NL_ASSERTION、ACTION：参考动作通常只是生成目标状态的一条路径，DB 检查允许另一条正确路径；只有 reward_basis 显式包含 ACTION 时才要求匹配动作。这一点决定了本项目不能用“必须完全照参考轨迹”代替业务正确性。

进一步核对 [EnvironmentEvaluator.calculate_reward](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/evaluator/evaluator_env.py)：重建 predicted/gold 环境、重放 gold actions、比较 agent/user DB hash、运行 env assertions，并按 reward_basis 组合奖励。**状态比较、重放、环境断言不是 EvalAnchor 原创。** 建议学习这些边界，但自建小型订单域和测试数据；本轮不复制其任务后改名，也不声称 τ-bench 兼容结果导入已经完成。

[τ² 论文](https://arxiv.org/abs/2506.07982) 的核心之一是 agent 与用户共同操作环境的 dual-control。本轮脚本用户只提供确定输入/确认，不模拟真实人的操作能力；不能把这个方案称为 τ² dual-control 复现。

### Inspect：已有 Agent 运行时，不应另造一个通用框架

Inspect 官方 [Agents 文档](https://inspect.aisi.org.uk/agents.html) 已提供 Agent 协议、ReAct、自定义 Agent、外部桥接、checkpoint 和执行限制。[Custom Tools](https://inspect.aisi.org.uk/tools-custom.html) 与 [`Tool` / `ToolError`](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/tool/_tool.py) 明确支持真实 Python 工具、状态和错误反馈。

本项目应把“订单领域、状态 oracle、跨运行证据审计和选择协议”作为自己的工作。可用 Inspect 自定义 Task/Agent/scorer 跑同一环境，或先做小而清晰的专用循环；无论选择哪种，都不应宣称发明工具循环、断点恢复或 Agent 抽象。若新 Agent 轨迹通过现有 importer，必须先扩展并验证对应 schema，不能把旧的单轮兼容声明自动延伸到多轮。

### Promptfoo：Agent 路径断言与 Inspect 融合也已存在

官方 [Python provider](https://github.com/promptfoo/promptfoo/blob/main/site/docs/providers/python.md) 定义 `call_api(prompt, options, context)`；[Python assertions](https://github.com/promptfoo/promptfoo/blob/main/site/docs/configuration/expected-outputs/python.md) 可取得 provider metadata 与 trace。

更直接的近邻是 [Evaluate OpenAI Agents](https://github.com/promptfoo/promptfoo/blob/main/site/docs/guides/evaluate-openai-agents-python.md)：已演示多轮 SQLiteSession、tool-used、tool-args-match、tool-sequence、goal-success、调用数和用量。文档还提醒混合模型/工具时不能凭聚合用量自动推断全部美元成本。

[Evaluate OSWorld with Inspect](https://github.com/promptfoo/promptfoo/blob/main/site/docs/guides/evaluate-osworld-with-inspect.md) 已把 Promptfoo 配置/报告、Inspect 执行、最终 VM 状态评分串起来。因此“Inspect + Promptfoo + 真正工具/状态”不能作为差异化本身。EvalAnchor 的证明责任是给出一个更小、易运行、业务约束明确、失败可重放的完整升级案例。

### 成本和鲁棒性：采用已有原则，不虚构研究贡献

[Unitxt 的模板/示例矩阵源码](https://github.com/IBM/unitxt/blob/main/examples/evaluate_different_templates_num_demos.py) 已使用 template、num_demos 和 group_by 评价多种设置。模板矩阵、分组、扰动不是新方法。

[AI Agents That Matter](https://arxiv.org/abs/2407.01502) 指出应同时看成本和准确率，并区分模型开发者与下游应用开发者的需求，重视 holdout 与可复现性。本项目采用这些原则；不声称首次提出成本约束的 Agent 评测或自动获得了可靠部署最优解。

## 5. 建议的具体业务闭环

用自建虚构订单与客户数据，做单用户、本地执行、每任务隔离的 OrderOps 环境。核心覆盖查询、取消、退款、地址变更及人工升级中的少数明确流程；不要为了工具数量加入无关功能。

建议任务类型包括：合法取消；已发货无法取消；满足/不满足退款窗口；仅预览不提交；用户拒绝确认；跨客户订单访问；同一请求重复送达；工具提交成功但响应丢失；价格/库存或订单版本在预览后变化；工具输出中夹带要求忽略政策的文本。具体支持哪些，以实现与案例为准。

每个 episode 应具有：

1. **可冻结初始条件**：任务/组/划分 ID，虚构客户会话、初始订单快照、政策版本、工具 schema、受控时钟、故障计划、允许操作与目标谓词。
2. **真实执行工具**：读取和写入的效果确实发生在本地状态中；每次调用返回工具观察。付款/退款金额统一整数分。模型不获得 oracle、参考动作或最终状态。
3. **可信授权来源**：身份来自环境会话，确认来自已记录的用户输入或脚本确认事件；不能让模型自己传 `confirmed=true` 就绕过确认。预览 token 应绑定订单、动作、金额、版本与确认范围。
4. **多轮执行**：模型看到真实工具结果，决定继续、纠正、查询提交状态或结束。对工具错误可以反馈恢复；不以 runner 偷偷重做写操作修复模型轨迹。
5. **可重放事件**：请求、原始响应、工具名/参数、状态前后摘要、返回值、事件序号、错误/超时、计费用量与终止原因。重新执行确定性工具可从初始状态复原保存的最终状态。
6. **结果判断**：合法目标已完成、无不允许状态变更、必要确认满足、最终回执与状态一致。正确路径可以不唯一。

**两个容易做错的地方：**

- 只比最终 DB 会漏掉中途的重复写入、泄露、错误操作再回滚。因此最终状态验收之外还需要事件层不变量。只比完整字节 hash 又可能误罚无关日志时间；应明确哪些业务字段属于目标状态，哪些事件属于独立安全规则。
- 环境拒绝非法写入并不说明 Agent 没有试图违规。分别记录 `attempted_policy_violation` 与 `executed_bad_effect`。否则强 guard 会掩盖坏 Agent，让所有配置都看起来安全。

自然语言礼貌、解释完整性和真实用户满意度仍未覆盖。可以另给人工诊断字段，但本轮不引入未校准的 LLM judge 作为决定业务成功的唯一裁判。工具沙盒也不是攻击者可执行任意 Python 的安全容器；只派发白名单、类型明确的本地函数。

## 6. 冻结开发/测试与扰动协议

先固定环境、oracle 和数据，再调整 Agent。建议至少有 12 个开发场景组、24 个最终测试场景组；每组可有 1 个基本输入及 1 个经核验的扰动输入。数字是覆盖建议，不是总体显著性的样本量证明，资源不足时宁可缩小并公开覆盖范围。

- **划分单位是场景实例组**：同一订单/客户事实、同一原题的语言改写、工具结果字段换序和重复运行全部留在同一 split。不同 ID 不能掩盖相同实例跨划分。
- **区分两种留出**：常规 test 可以共享业务类型，但实体与具体状态实例独立；若还要声称组合泛化，另留未在 dev 使用的政策条件组合。不能把同模板换 ID 说成未见任务类型。
- **冻结清单**：保存 case 定义、初始状态、policy/tool/oracle 版本、分组、split、故障seed、扰动映射、选型规则和候选配置摘要。发布前后都验证清单未变。
- **语义保持扰动**：实体重命名、无关字段排序、已人工核对的中英改写；预期任务结果应保持相应映射。保留原题关系，不把每条扰动当独立人群样本。
- **语义改变扰动**：取消确认、变更订单归属、退款超窗、版本冲突；对应 oracle 必须明确改变。不要把这类变化合并成“鲁棒一致率”。
- **测试后改进**：允许修 bug 和迭代，但保留原失败与版本；看过最终 test 后再修 prompt，该 test 就不再是未见验证集。下一轮需要新 confirmatory 集或清楚标注探索性结果。

固定 authored suite 仍不等于生产分布的 IID 样本。可以报告有限合同验收通过，但不能据此给总体部署安全保证；应与原有统计 `INCONCLUSIVE` 结果并列，避免人为把 sampling 标成 independent 来取得 PASS。

## 7. 可回答问题的实验，而不是参数堆砌

第一阶段先用不调用模型的三类策略验证环境和 scorer：合法 oracle 策略；违规/重复写入策略；只说成功不执行的策略。再用有界真实推理做下面的实验。

| 对照 | 固定什么 | 改变什么 | 能回答什么 |
|---|---|---|---|
| 模型对照 | 相同 policy、工具、prompt、任务、步数/输出上限 | 实际可用的两个模型/配置 | 升级模型是否改善任务与关键失败 |
| 提示词对照 | 同一模型、环境、任务、预算 | 简洁基准 vs 明确核验/确认/恢复协议 | 观察到的改进是否来自可解释的流程提示 |
| 预算消融 | 同一模型/prompt/任务 | 两个预先选定的步数预算 | 更多步骤解决了什么，是否只是增加成本 |
| 故障/扰动切片 | 同一配置、关联基础任务 | 已定义的故障或语义有效变换 | 系统是否依赖理想接口和固定措辞 |

不要在同一次对照中同时更换模型、prompt 和环境 guard，再把效果归因于模型。步数上限须定义为模型请求轮数还是工具调用数；应由 oracle 证明基本预算有能力完成被测任务。若低预算连最短合法流程都容不下，结果说明预算不可行，不能解释成模型不会规划。

建议在 dev 上选候选和有限实验规模，再冻结 test 运行基准与候选；其他预注册矩阵可以作为描述性对照，但不能不断从最终 test 中挑胜者。两次重复能显示有限稳定性，不能把同组次数当新增独立任务。`pass^k` 或“全重复通过率”若使用，必须明确公式与试验次数。

预算建议：整个任务使用同一持久化账本，把既往实际开销计入总额；分阶段设开发预检、正式矩阵与保留额度。5 美元是授权上限而不是花费目标。可把可调度模型费用限制在 4.50 美元以内，为未知失败收费保留余量，且不超过剩余额度。实际分配以最新官方价目、可用模型与 dry-run 完整请求估算为准，本文没有核验价格，也不指定哪个新模型必然可用。

每次请求前原子预留其最坏可控预算；输入上限包括累计对话、工具 schema 与工具结果，输出有硬上限。并发、重试、重启共享同一账本；超时请求可能仍计费，不能直接释放预留。若无法给出有根据的预留上界，应降低规模或停下，不把次数上限宣传成账户账单硬上限。优先官方用量回执，成本标签为估算；未知成本独立列出，不能计为零。

## 8. 建议的验收门槛

以下是实施建议，须在看最终 test 结果前固定。

| 层次 | 必须展示的证据 | 不通过时的行为 |
|---|---|---|
| 环境正确性 | 独立测试所有写操作前置条件、授权、幂等、整数金额、隔离与预设故障；合法 oracle 能完成所有标为可完成的任务 | 先修环境，不把环境 bug 算成模型失败 |
| 评分可信度 | 三类反例正确判定；不同正确路径通过；中途非法副作用不能被最终状态恢复掩盖；空操作不能在目标应改变时获成功 | 不执行正式模型矩阵 |
| 证据完整性 | 完整冻结网格；每步原始请求/响应；事件重放一致；篡改输出、工具参数、状态、分组或价格版本会被发现 | 比较无效，保留原记录 |
| 实际运行 | 至少两个真实配置在同一冻结测试集运行，原失败保留，能区分 provider/harness/model failure；预算账本符合总上限 | 标明不足，不能用 fixture 代替真实结果 |
| 关键业务约束 | 测试集上实际越权写入、重复退款、跨客户泄露等预定义严重副作用为 0；危险尝试单独列出并设置候选门槛 | 拒绝该候选，不用平均分抵消 |
| 有限合同决策 | 例如任务完成率至少 90%、关键组无新增失败、真实错误率为 0、估算单任务成本不超预注册预算；同时展示分母和切片 | 明确失败原因；不是把协议改到能通过 |
| 改进闭环 | 选择一个 dev 的真实失败，按轨迹定位原因、只改一个有解释的因素；在冻结 test 评估，包括未改善案例 | 可以结论是“改进未成立”，项目仍完整 |
| 交付 | 干净克隆可离线跑环境/评分器/报告；可选 API 命令默认 dry-run；GitHub CI 实际运行记录；论文/许可/限制准确 | 修复可复现性或降低声明范围 |

90% 等门槛是一个可讨论的示例，不是文献给出的安全标准。有限合同全部通过与统计总体通过是不同结论：建议报告分开显示 `contract_acceptance`、`comparison_validity`、`population_inference`，避免现有三态统计门禁让使用者误解“为什么任务全对仍不准发布”。任何字段名称以实际 schema 为准。

建议报告优先回答：哪一配置、多少真实任务、完成多少、哪些关键约束失败、共发多少模型请求、已知/未知费用、相对基准哪些实例改善或退化、选择理由。然后才给总图。增加 episode 详情页的状态差异和工具时间线，会比继续增加通用排行榜模块更有价值。

## 9. 做与不做，及重开条件

**本轮建议做：**自建订单沙盒与脚本用户；确定性状态/事件 oracle；原始轨迹和重放；开发/测试冻结；少量有效扰动；真实多配置实验；统一预算账本；真实失败诊断；可运行文档、CI、结果报告和本人 GitHub 发布。

**本轮不承诺：**真实电商支付写入、真实客户隐私数据、完整客服语义质量、语音双工、付费用户模拟器、未经人工校准的 LLM judge、自动 prompt 搜索、学习型路由、全领域榜单、分布式多租户平台、密码学不可抵赖、总体上线安全保证。

如果所有方案都满分，应检查任务难度和 oracle，而不是马上扩模型表；优先加入新的合法业务组合与故障恢复任务。若差异主要来自结构化格式而非业务执行，应改用实际工具调用接口并单独计协议解析失败。若 API 费用或调用延迟约束严厉，应先减少探索矩阵而保留两个核心对照与独立 test。若真实用户需求变成开放文本服务质量，应重开人工标注与 judge 校准路线，而不是继续把确定性字段评分扩名为“满意度”。

求职讲解的真实贡献可以是：**完成了从领域建模、环境正确性、真实 Agent 执行、评测有效性、成本约束到版本选择的完整工程，并且能展示一次失败如何被发现、定位和验证。** 不需要把它包装成新的基准算法，也不能把一个缩小 τ-bench 称作首次提出的研究系统。
